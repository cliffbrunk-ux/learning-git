01

Repository repo

The project folder, tracked by Git and hosted on GitHub et al.

What it does

A repository is an ordinary folder plus a hidden .git directory sitting inside it. That directory is the whole database: every snapshot you have ever saved, every branch name, and every setting. Delete .git and you are left with plain files and no history.

Because the history lives in the folder, Git works entirely offline. GitHub is not Git — it is one popular place to keep a copy of the repository so other people can reach it.

Considerations

  • Add a .gitignore before your first commit. Build output, node_modules/, and .env files do not belong in history.
  • Anything you commit is permanent. A leaked API key is not fixed by deleting it in a later commit — rotate the key.
  • Git is built for text. Large binaries (video, PSDs) bloat the repo forever; use Git LFS or keep them elsewhere.
  • One repository per deliverable project. Resist the urge to make one giant repo of unrelated things.

02

Clone

Download a copy of the code to your machine.

What it does

git clone <url> copies a remote repository onto your machine — not just the current files, but every commit ever made. You end up with a fully independent repository that happens to remember where it came from, under the nickname origin.

You clone once. After that you use pull to stay up to date; cloning again into a fresh folder is a common beginner reflex and almost never what you want.

Considerations

  • Clone with HTTPS to get started; move to SSH once you are tired of typing tokens.
  • You are cloning into the folder you are currently in — cd somewhere sensible first.
  • A clone of someone else's repo gives you no write access. To contribute, fork it first, then clone your fork.
  • Huge repos: --depth 1 grabs only recent history, much faster, but limits what you can inspect.

03

Branch

A safe parallel timeline to the main codebase.

What it does

A branch is a movable pointer at one commit. Creating one is instant and costs nothing — Git is not copying your files, it is writing a 40-character hash into a small file. That cheapness is the whole point: make a branch for every idea, and throw away the ones that do not work.

git switch -c feature/nav creates and moves onto a new branch. Work there, and main stays exactly as it was.

Considerations

  • Branch from an up-to-date main. Branching off a stale one is how you invent conflicts.
  • Keep branches short-lived — days, not months. Long branches drift far from main and merge painfully.
  • Use a naming convention the team can scan: feature/, fix/, docs/.
  • One branch, one intent. A branch that does three unrelated things is unreviewable.

04

Commit

A snapshot + message describing your changes.

What it does

A commit records the state of the staged files, along with an author, a timestamp, a message, and a pointer to the commit before it. Those pointers chained together are your history.

The staging area is the part beginners skip past. It exists so you can commit some of your edits and not others — turning a messy afternoon into a few clean, reviewable steps.

Considerations

  • Write the message for the person reading it in six months. Explain why, not what — the diff already says what.
  • Imperative mood, by convention: "Add empty state", not "Added empty state".
  • Small, focused commits are easier to review and to revert. git add -p stages hunk by hunk.
  • git commit --amend fixes the last commit — but never amend something you have already pushed and shared.

05

Push / Pull

Upload to / download from the hosted repository.

What it does

Commits live only on your machine until you push them. git push sends your branch's new commits to the remote; git pull brings down commits other people have pushed and merges them into your branch.

pull is really two commands in a trench coat: fetch (download) followed by merge (combine). Running git fetch on its own is a safe way to look before you leap.

Considerations

  • Pull before you start work, and before you push. Most conflicts are just a skipped pull.
  • Unpushed work exists in exactly one place. A dead laptop is a real backup strategy failure.
  • git pull --rebase avoids littering history with "Merge branch 'main'" commits.
  • Never push --force to a shared branch — it deletes other people's commits. --force-with-lease is the safer relative.

06

Diff

The visual difference between two versions of code from two different branches.

What it does

A diff compares two states and shows only what changed, line by line: removals prefixed -, additions prefixed +. It is how you check your own work before committing, and how reviewers read a pull request without opening every file.

git diff shows unstaged edits, git diff --staged shows what is about to be committed, and git diff main..feature compares two branches.

Considerations

  • Read your own diff before every commit. It catches stray console.logs and debug code.
  • A changed line shows as one removal plus one addition — Git has no concept of "edited".
  • Reformatting a whole file drowns the real change. Keep formatting commits separate from logic commits.
  • Diffs of images or binaries are useless in the terminal; GitHub's image view is far better.

Resources

  • git diff reference
  • delta a much nicer terminal diff viewer

07

Merge

Combine a branch back into another branch.

What it does

git merge feature/nav, run while you are on main, takes everything that happened on the feature branch and joins it into main. When both branches have moved on, Git creates a merge commit — a commit with two parents, which is what preserves both timelines.

If main has not moved at all, Git skips the merge commit and simply slides the pointer forward. That is a fast-forward.

Considerations

  • Merging is non-destructive — nothing is rewritten, so it is the safe default on shared branches.
  • The cost is a busier graph. Teams that dislike this reach for rebase or squash merges instead.
  • Merge into an updated main, and run the tests after merging — a clean merge is not a working merge.
  • Halfway through a bad merge, git merge --abort puts everything back.

08

Rebase

Replay your commits on top of the latest main.

What it does

Rebasing lifts your branch's commits off their old starting point and reapplies them, one at a time, on top of the newest main. The result is a straight line of history that looks as though you started your work this morning.

The crucial detail: those are new commits with new hashes. The originals are discarded. That is why rebasing is powerful locally and dangerous publicly.

Considerations

  • The golden rule: never rebase commits that other people have already pulled.
  • Perfect for tidying your own branch before opening a PR: git rebase main.
  • git rebase -i lets you squash, reorder, reword, and drop commits interactively.
  • Conflicts can resurface once per replayed commit. git rebase --abort is always available.

09

Merge conflict

Two changes touched the same lines; you choose.

What it does

When two branches change the same lines of the same file, Git refuses to guess. It stops, writes both versions into the file wrapped in <<<<<<< / ======= / >>>>>>> markers, and hands the decision to you.

You edit the file until it reads the way it should, delete the markers, then git add it and continue. A conflict is not an error — it is Git being careful.

Considerations

  • Resolve by meaning, not by picking a side. Sometimes the right answer is neither version.
  • Search the file for <<<< before committing — shipped conflict markers are a classic embarrassment.
  • Always re-run the app after resolving. A syntactically valid resolution can still be nonsense.
  • Prevention beats cure: small branches, frequent pulls, and agreed file ownership.
  • Stuck? git merge --abort returns you to before the merge, every time.

10

Pull Request PR

“Please review and merge my branch.”

What it does

A pull request is a GitHub feature, not a Git one. It says: here is my branch, here is the diff, please look at it before it becomes part of main. It gives the team a place to comment on specific lines, run automated checks, and record approval.

When it merges, GitHub offers three shapes: a merge commit, a squash (all your commits collapsed into one), or a rebase. Most product teams squash.

Considerations

  • Keep them small. A 200-line PR gets a real review; a 2,000-line PR gets "LGTM".
  • Write the description for a reader with no context: what changed, why, and how to test it. Screenshots for UI work.
  • Open a draft PR early to get CI running and signal what you are working on.
  • Review comments are about the code, not the person. Reply to every one, even if only to say you disagree.
  • Link the issue it closes (Closes #42) so GitHub ties them together automatically.

11

Issue

A ticket: bug, feature, or task.

What it does

An issue is a unit of work with a conversation attached: a bug report, a feature request, or a task. It has a number, a title, labels, an assignee, and a thread. It is the lightest project-management tool that lives next to the code it describes.

Mentioning #42 anywhere — a commit message, a PR, another issue — creates a permanent cross-link. Merging a PR that says Closes #42 closes the issue for you.

Considerations

  • A good bug report has three parts: what you did, what you expected, what happened instead.
  • One issue, one problem. Bundled issues never fully close.
  • Labels are only useful if the set is small and everyone applies them the same way.
  • Search before opening — duplicates fragment the discussion.
  • Issue templates make good reports the default rather than the exception.
